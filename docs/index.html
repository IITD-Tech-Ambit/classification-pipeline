1 · Executive summary

The existing classification (66,235 of 69,677 papers labeled) is unreliable because it was produced by a single unconstrained model pass over an unvalidated taxonomy: 50,758 distinct free-text topics (≈ one per paper), editorials and abstract-less items force-labeled, overlapping theme definitions, and no confidence or audit trail. Critically, the domain/subdomain/topic layers themselves came out of that same noisy process — only the 9 thematic areas are trustworthy human-approved structure.

This plan therefore does two jobs in strict order. First it regenerates the taxonomy bottom-up from the corpus: papers are assigned to the 9 fixed themes by a multi-model ensemble, then domains and subdomains are discovered by clustering within each theme — a node exists only if enough papers, cluster stability, and separation tests justify it, and a human curator approves every node. Topics become a small controlled vocabulary extracted from member papers; free text is structurally impossible. Second, it classifies every paper against that frozen taxonomy by independent agreement: an embedding classifier and two LLMs of different families must agree before a label is written; disagreements escalate to a much larger pooled model; survivors of all four go to a small human review queue. "Unclassifiable" is a legitimate, stored outcome.

On compute: the main passes run data-parallel — each laptop independently runs a 30B-class Mixture-of-Experts model (feasible at ~30 tok/s on 6 GB VRAM via llama.cpp expert-offloading) against a shared MongoDB job queue. The two GPUs are pooled over the 1 Gbps backbone only for the escalation model that cannot fit on one machine (prima.cpp, fallback llama.cpp RPC). Nothing runs on the full corpus until it clears a measured accuracy bar on a human-verified gold set, and a 200-paper benchmark run fixes the real schedule before any multi-week job starts.

Two structural decisions define everything downstream:

  1. Themes before structure. Because only the 9 themes are trusted, papers get a high-confidence theme label first (a 9-way choice small models handle reliably), and taxonomy discovery then happens inside each theme pool. Noise never shapes structure: papers that fail the gate or get no ensemble agreement are excluded from clustering.
  2. Agreement, not confidence. A small self-hosted model's self-reported confidence is worthless; agreement between independent systems is not. Every label is the product of a vote between an embedding classifier and two LLMs from different training lineages, with a bigger model adjudicating disagreements.

4 · P0 — Data hygiene & embedding foundation RULESGPU-LIGHT

4.1 Gate (before any GPU cycle is spent)

  • document_type ∈ {Editorial, Erratum, Note, Letter, Book review} → unclassifiable(non_research)
  • Abstract missing or "(No abstract available)" and title < ~6 words → unclassifiable(insufficient_text). Papers with a substantive title but no abstract stay in, flagged title_only (voters see the flag; thresholds for auto-accept are stricter for them).
  • Deduplicate on document_eid; normalize whitespace/HTML entities in abstracts; drop copyright boilerplate suffixes ("© 2009 IEEE").
  • Non-English detection (fast heuristic) → route to a small translated-title pass or unclassifiable(language).

Expected removal: roughly 4–6% of the corpus — exactly the slice that produced v1's most visible junk.

4.2 Embedding bake-off, then embed everything once

Two candidates: bge-large-en (strong general retrieval; already measured on this hardware — 70k docs ≈ 1 hour) and SPECTER2 (trained specifically on scientific papers with citation signal — often better for clustering research abstracts). Run both on the theme mini-gold set (§6.1) and on a clustering silhouette check; keep the winner as the single embedding space used everywhere (theme profiles, clustering, candidate pruning, topic matching). Embeddings are computed once, stored, and reused by every later phase.

5 · P1 — Theme scope notes HUMAN

For each of the 9 themes, a one-paragraph scope statement with explicit inclusion and exclusion rules plus 3–5 boundary examples. The known collision must be resolved in writing: e.g. quantum algorithms / quantum ML → AI-ML theme; quantum hardware, qubits, photonics, semiconductor fabrication → Quantum Technologies theme. Similar boundary contracts are needed for at least: AI-applied-to-X vs X (an ML-for-drug-discovery paper → Healthcare or AI?), materials-for-energy vs materials science, and embedded/IoT vs communication.

These scope notes are the single highest-leverage artifact in the whole system. They are injected verbatim into every LLM prompt, they brief the human labelers, and they are the thing that gets edited (instead of prompts or models) whenever a confusion pair shows up in evaluation. Budget real faculty time here.

6 · P2 — Theme assignment pass GPU-HEAVY

6.1 Theme mini-gold set first

~180 papers (20 per theme, stratified by department) labeled by the team against the scope notes. Cheap (themes are a 9-way choice) and done in a day. It calibrates the theme-level ensemble and settles the embedding bake-off before any big run.

6.2 Adaptive three-voter ensemble at theme level

  • Voter 1 — embeddings: similarity to theme profiles (name + scope note + boundary examples) plus a logistic head trained on the mini-gold; a hand-written Scopus subject_area→theme prior and an iitd_authors department prior enter as features, never as hard rules.
  • Voter 2 — LLM A: 30B-class MoE (Qwen3-A3B family, Q4), constrained choice over 9 themes with scope notes, self-consistency ×3 (temperature ≈ 0.7, majority).
  • Voter 3 — LLM B: different-family model (Phi-4-14B class, Q4), same task, greedy.
  • Adaptive compute: where Voter 1's calibrated margin is very high (tuned so that slice is ≥98% correct on mini-gold), LLM voters are skipped. Expect 50–60% of papers to short-circuit — this halves the pass without touching quality, because the skipped slice is measured, not assumed.

Outputs per paper: primary theme, optional secondary themes (high absolute score + one LLM confirmation), or theme_undecided → these papers sit out of taxonomy induction and re-enter at P5 escalation.

7 · P3 — Taxonomy induction: domains, subdomains, topics GPU-LIGHTHUMAN CURATION

The core principle: node count is an output of evidence, not an input. A node exists only if it passes mass, stability, and separation tests — then a human approves it. The LLM's only job is to name what the data found.

Design details that keep it strict

  • Primary-theme pools only. Interdisciplinary papers cluster in their primary theme; secondary membership is handled at classification time, so it never duplicates structure.
  • HDBSCAN noise points don't shape structure. Outlier papers simply don't vote on the taxonomy; they still get classified in P5 (into approved nodes, or unclassifiable).
  • Expected shape: ~4–7 domains per theme (likely fewer than the current 35 overall) and realistically 80–130 subdomains instead of 177 — every one backed by a real paper population. The current pathology (subdomains with 38 papers) cannot recur.
  • Every node ships with artifacts: centroid vector, auto-drafted scope description (SME-edited), keyterm list, example papers. These become the profiles used for candidate pruning in P5 — the taxonomy and the classifier share one geometry.
  • SME effort is bounded: reviewing ~50 domain candidates and ~120 subdomain candidates with names, keyterms and examples pre-attached is days of work, not a relabeling project. Faculty review the final tree per theme; the team does the first curation pass.
  • Topics are extracted, never generated: a phrase enters the vocabulary only if it appears in ≥5 distinct member papers; hard cap 10–15 per subdomain; total vocabulary lands ~800–1,800 versus 50,758 today.

8 · P4 — Gold set & acceptance bar HUMAN

Stratified sample of 400–500 papers (department × document type × abstract presence × theme), labeled against the frozen taxonomy_v2 with full paths. Because the categories were derived from the corpus, labelers should find choices natural — friction during labeling is itself an early warning that a node is bad.

The gold set serves three separate functions: training (the embedding voter's calibrated head), threshold tuning (ensemble margins, adaptive short-circuit cutoffs, secondary-theme bar), and acceptance:

Hard rule: nothing runs on the full corpus until, on held-out gold data, the auto-accepted slice reaches ≥95% at theme level and ≥85% at full-path level, with everything below the bar routed to escalation or review — routed doubt is a feature; silent error is the failure mode.

Why this shape (research-backed)

  • If a model fits on one node, never split it. Community benchmarks show RPC workers slow down a model that already fits locally; RPC's value is capacity, not speed. Classifying 70k independent papers is embarrassingly parallel — two full model copies on a shared queue is a true 2×.
  • The MoE unlock: 30B-class MoE models (~3B active) run at ~30 tok/s on a 6 GB card with expert tensors in system RAM (--n-cpu-moe / -ot ".ffn_.*_exps.=CPU") — near-30B quality per laptop with zero network dependence. Hard requirement: ≥32 GB system RAM per laptop (~20 GB for Q4 expert weights). If one laptop has 16 GB, that machine runs a smaller MoE or an 8B dense voter instead.
  • Pooling tier: the adjudicator is a 32B-class dense model (different lineage and scale than both voters) split across both machines. prima.cpp is purpose-built for low-VRAM home clusters (pipelined-ring parallelism, 5–17× lower time-per-token than llama.cpp RPC on such setups; ~26 tok/s reported for 32B with speculative decoding on four devices); llama.cpp RPC is the mature fallback. On 1 GbE expect meaningful decode overhead versus 10 GbE — acceptable because this tier sees only the ~10–15% disagreement slice and outputs are short. Wired Ethernet always; never Wi-Fi. A 70B adjudicator is an optional stretch goal if benchmarks show acceptable ms/token.
  • Both voters visit every paper: the queue alternates model batches across laptops (or papers swap machines halfway) so V2 and V3 each see the whole corpus regardless of which laptop leased the job.
  • Fault tolerance: jobs carry status/lease/worker/attempts; leases expire and return orphaned work to the pool; every model output is checkpointed on production. Multi-week runs on laptops will be interrupted (reboots, thermals) — the design assumes it.
  • Reproducibility: model files pinned by hash; sampling seeds recorded; every output row stores model version + prompt template version + taxonomy version.

12 · P6 — Evaluation & rollout

  1. Gold-set run: full pipeline on held-out gold; per-theme confusion matrices for each voter and the ensemble.
  2. Fix by editing scope notes, not prompts or models. The worst confusion pairs get sharper exclusion rules; persistent offenders trigger taxonomy review (maybe two nodes should be one). Iterate until the §8 bar is met.
  3. 200-paper benchmark run on both laptops with real prompts and batch settings → measured tok/s, per-paper latency, projected completion date, and a dry run of queue/checkpoint/write-back. Never extrapolate a multi-week job from theory.
  4. Backfill the full corpus. Bonus signal: each backfill paper's cluster of origin from P3 acts as a prior — ensemble-vs-cluster disagreement is itself a review-queue trigger.
  5. Diff v1 vs v2. Expect large disagreement (that is the point). Spot-check the biggest movers per theme; publish a short change report so stakeholders understand why counts shifted.
  6. Flip the application to read classification_v2; keep v1 one release cycle, then archive.

  • Ingest volume is small — steady state runs on one laptop; escalation is rare.
  • Taxonomy evolution is governed, not ad-hoc: new nodes must pass the same mass/stability tests as P3; every node change bumps taxonomy_version and triggers reclassification only of affected papers (their embeddings are cached, so this is cheap).
  • Quarterly: threshold re-tune on the grown gold set; model refresh evaluated on gold before adoption (the small-model landscape moves fast — any swap must prove itself on your data first).
